# Idle accessibility audit

**Scope:** Electron browser and Astro landing page, current workspace snapshot, 31 October 2026. **Method:** read-only source and existing-check review; no assistive-technology, visual, browser or platform runtime audit was performed. File/line references point to the inspected working tree, including existing uncommitted changes. Priorities describe user impact, not formal legal determinations. WCAG mappings for desktop software should be assessed using WCAG2ICT and the applicable EN 301 549 provisions; web WCAG requirements are not automatically identical to every software requirement.

## Executive summary

**Readiness: not ready to claim WCAG 2.2 AA or EN 301 549 conformance.** The source has useful foundations: named controls and landmarks, native menus, a keyboard-adjustable sidebar separator, workspace context-menu keyboard support, tab reordering alternatives, profile isolation, and site skip navigation. Important gaps remain in browser chrome scaling, progress semantics, focus and AT verification, and site contrast. The cached-profile architecture correctly detaches inactive views in code, but accessibility-tree exposure and focus after reattachment are **untested**. A source audit and passing unit tests cannot establish conformance.

**Status legend:** Confirmed = directly demonstrated by source or a stated calculation; Risk = implementation warrants verification, not a proven failure; Untested = no runtime/AT evidence. No P0 blocker is asserted without end-to-end evidence.

## Findings

### P1 — Major

1. **Browser chrome has no implemented text/zoom scaling control.** **Confirmed implementation gap; conformance impact requires runtime verification.** [main/index.ts:358](../src/main/index.ts#L358) applies zoom to the active page WebContents, while chrome uses fixed pixel sizes and a 760 × 520 minimum window ([styles.css:62](../src/renderer/src/styles.css#L62), [main/index.ts:61](../src/main/index.ts#L61)). People needing larger browser controls may be unable to enlarge chrome independently of pages. **Mapping:** WCAG 1.4.4, 1.4.10 as applicable; EN 301 549 11.7/user preferences. **Minimal fix:** add a chrome text/zoom setting or reliably honor OS text scaling; test 200% text and 400% equivalent reflow without losing controls. **Verification:** source only; Windows text scaling, macOS larger text and actual clipping untested.

2. **Landing-page small secondary text has insufficient contrast.** **Confirmed by token calculation.** Hero release/status text uses `text-charcoal-light` ([Hero.astro:58](../website/src/components/Hero.astro#L58)); its `#828a83` on `#fbfaf7` ([global.css:4](../website/src/styles/global.css#L4)) is approximately **3.40:1**, below 4.5:1 for normal text. Footer also uses the token ([Footer.astro:17](../website/src/components/Footer.astro#L17)). Low-vision users may miss release availability. **Mapping:** WCAG 1.4.3 AA; EN 301 549 9.1.4.3 for web. **Minimal fix:** darken the text token for each actual surface to at least 4.5:1. **Verification:** calculated from specified solid colours, not a rendered pixel/complete contrast audit; other opacity and blended surfaces remain unmeasured.

3. **Download progress has no programmatic name or explicit status announcement.** **Confirmed markup gap.** The generated `<progress>` has `value` and `max` but no label or association to its filename; changing download status is plain text ([main.tsx:367](../src/renderer/src/main.tsx#L367)). A screen reader may announce an unidentified progress bar and miss completion/failure. **Mapping:** WCAG 4.1.2 and 4.1.3; EN 301 549 11.5.2.5/11.5.2.8, as applicable. **Minimal fix:** associate each progress control with its filename and announce meaningful completion/failure once via a polite status. **Verification:** static markup; actual announcements untested.

4. **Profile switching can discard live pages and focus after cache eviction.** **Confirmed lifecycle; AT impact untested.** Inactive contexts are detached ([main/index.ts:908](../src/main/index.ts#L908)); switching among more than two profiles can dispose an evictable context ([main/index.ts:978](../src/main/index.ts#L978)), closing cached WebContents ([main/index.ts:930](../src/main/index.ts#L930)). Reopening that profile recreates views from persisted state, not the live DOM, caret, form or screen-reader position. This can interrupt users who rely on stable focus or unsaved content. **Mapping:** WCAG 2.4.3 and 3.2.1 (assess the specific interaction), EN 301 549 11.5.2.3/11.5.2.4. **Minimal fix:** preserve live contexts where feasible; if eviction is necessary, protect unsaved sessions, restore a predictable focus target and communicate loss/reload. **Verification:** control flow confirmed; NVDA/JAWS/VoiceOver tree and focus behaviour untested.

5. **Split pane focus is tied to pointer interaction, without an explicit pane-cycle command.** **Confirmed missing explicit mechanism; practical keyboard access is untested.** Toolbar selection uses `onPointerDown` ([main.tsx:50](../src/renderer/src/main.tsx#L50)); a page focus event updates the active pane ([main/index.ts:270](../src/main/index.ts#L270)). The registry has tab cycling but no pane-focus cycle ([shortcuts.ts:1](../src/main/shortcuts.ts#L1)). Keyboard users may not be able to move predictably among page views and their chrome; keyboard focus on a pane toolbar alone does not call `pane-focus`. **Mapping:** WCAG 2.1.1, 2.4.3; EN 301 549 11.2.1.1/11.5.2.3. **Minimal fix:** update pane selection on keyboard focus and add discoverable next/previous pane and chrome↔page commands. **Verification:** code inspection; keyboard and AT traversal across native views untested.

### P2 — Moderate

6. **Split resizing is not implemented despite site copy.** **Confirmed implementation gap.** Split ratios are rendered from `tree.ratio` ([main.tsx:61](../src/renderer/src/main.tsx#L61), [main/index.ts:184](../src/main/index.ts#L184)); no split resize command or interactive divider exists in the inspected source, while the site says “Drag divider to adjust ratio” ([FeatureSplit.astro:112](../website/src/components/FeatureSplit.astro#L112)). Users cannot adjust pane size by pointer or keyboard. **Mapping:** WCAG 2.1.1 and 2.5.7 apply if resizing is offered; current mismatch is a functional/accessibility gap, not an automatic dragging-criterion failure. **Minimal fix:** correct the claim or implement a labelled separator with keyboard and single-pointer non-drag alternatives. **Verification:** static inspection; no runtime test.

7. **Profile radio-group keyboard focus does not explicitly follow selection.** **Confirmed missing focus handling.** The arrow-key handler requests a profile switch but does not focus the newly checked radio ([main.tsx:317](../src/renderer/src/main.tsx#L317)); the prior radio becomes `tabIndex=-1` after state updates. Users may hear an old choice or lose their position. **Mapping:** ARIA 1.2 radiogroup and APG radio pattern; WCAG 2.4.3/4.1.2. **Minimal fix:** move focus to the newly selected radio after successful switching and restore it on failure. **Verification:** static code; re-render/native focus interaction untested.

8. **Closing or switching overlays lacks consistent focus restoration.** **Confirmed gaps; impact depends on entry path.** Command menu close only updates state ([main.tsx:366](../src/renderer/src/main.tsx#L366)); downloads close similarly ([main.tsx:367](../src/renderer/src/main.tsx#L367)); settings close focuses the page or renderer, not necessarily the initiating control ([main/index.ts:225](../src/main/index.ts#L225)). By contrast, Workspace popovers explicitly restore their anchor on some paths ([WorkspaceActions.tsx:24](../src/renderer/src/WorkspaceActions.tsx#L24)). When a focused control is removed, keyboard and screen-reader users may be left at an unpredictable location. **Mapping:** WCAG 2.4.3; APG focus practices. **Minimal fix:** retain each opener and restore it when still available, otherwise select a documented logical fallback. **Verification:** static inspection; actual OS focus untested. These are non-modal panels; a modal focus trap should not be added unless their modality changes.

9. **Settings initial focus is deliberately visually hidden.** **Confirmed CSS/code combination; visual impact untested.** Settings moves focus to its heading ([SettingsPage.tsx:19](../src/renderer/src/SettingsPage.tsx#L19)) and the heading rule suppresses its outline ([styles.css:349](../src/renderer/src/styles.css#L349)). Keyboard users can have no visible focus cue on entry. **Mapping:** WCAG 2.4.7; APG focus visibility. **Minimal fix:** provide a visible focus indication for the heading or focus a visibly indicated first relevant control. **Verification:** source; actual painted focus untested.

10. **Workspace and profile transitions lack explicit selection announcements.** **Confirmed omission; AT behaviour untested.** Selection is represented by `aria-current`/`aria-checked` ([main.tsx:317](../src/renderer/src/main.tsx#L317), [main.tsx:322](../src/renderer/src/main.tsx#L322)); the live region displays `browser.announcement`/drag messages ([main.tsx:355](../src/renderer/src/main.tsx#L355)), but Workspace/profile switch paths do not set an announcement ([main/index.ts:378](../src/main/index.ts#L378), [main/index.ts:967](../src/main/index.ts#L967)). Shortcut and swipe switches can leave focus elsewhere, so a change may not be communicated. **Mapping:** WCAG 4.1.3, 4.1.2 where applicable; EN 301 549 11.5.2.5/11.5.2.8. **Minimal fix:** announce the selected Workspace/Profile once for non-focus-moving switches. **Verification:** source only; AT announcements untested.

11. **Accessible context-menu access and touch parity differ by control.** **Risk.** Workspace icons explicitly support Context Menu/Shift+F10 and use a labelled menu ([main.tsx:322](../src/renderer/src/main.tsx#L322)); tab menus are attached to `onContextMenu` ([main.tsx:308](../src/renderer/src/main.tsx#L308)) and offer Move, Split and Group alternatives ([main/index.ts:763](../src/main/index.ts#L763)), but there is no explicit visible tab menu control or explicit keyboard handler. Chromium/OS context-menu key dispatch and touch long-press are not established by source. **Mapping:** WCAG 2.1.1, 2.5.7, 4.1.2; EN 301 549 11.2.1.1. **Minimal fix:** verify native keyboard dispatch on both platforms and add an accessible tab actions trigger/keyboard handler where needed; provide a discoverable touch alternative. **Verification:** static inspection only. Workspace context actions provide non-drag reorder; tab context menu supplies non-drag move and split.

12. **Small resize target and OS contrast/zoom behaviour need validation.** **Confirmed size; criterion outcome untested.** The sidebar separator is 8 CSS px wide ([styles.css:119](../src/renderer/src/styles.css#L119)), with keyboard arrows/Home/End ([main.tsx:353](../src/renderer/src/main.tsx#L353)). It may be difficult to acquire by pointer; WCAG 2.5.8 spacing/equivalent exceptions must be assessed in context. Forced-colour CSS changes only some surfaces ([styles.css:158](../src/renderer/src/styles.css#L158)), and the window disables material in high contrast ([main/index.ts:56](../src/main/index.ts#L56)); neither proves system colours, focus, or page accessibility. **Mapping:** WCAG 2.5.8/1.4.11, EN 301 549 11.7; Windows contrast themes. **Minimal fix:** enlarge hit area without increasing the visible divider and test system colours and focus in real contrast themes. **Verification:** CSS inspection; rendered spacing, UIA and forced-colours untested.

13. **Workspace menus and emoji pickers need non-modal focus/AT review.** **Risk.** Workspace popovers use `menu`/`menuitem`, arrow-key logic and initial focus ([WorkspaceActions.tsx:26](../src/renderer/src/WorkspaceActions.tsx#L26), [WorkspaceActions.tsx:32](../src/renderer/src/WorkspaceActions.tsx#L32)); emoji pickers are portalled dialogs around a third-party widget ([WorkspaceEmojiPicker.tsx:29](../src/renderer/src/WorkspaceEmojiPicker.tsx#L29)). Dialog mode switching and asynchronous picker focus, focus restoration after delete, outside click, Tab and Escape need actual testing. **Mapping:** ARIA 1.2/APG menu and dialog patterns; WCAG 2.1.1/2.4.3/4.1.2. **Minimal fix:** test and adjust focus entry, Tab/Escape and restoration according to whether each popup is modal; do not assume the picker is inaccessible without testing it. **Verification:** static only.

14. **Website fixed elements may obscure focus at zoom/reflow.** **Risk.** A sticky header ([Navbar.astro:14](../website/src/components/Navbar.astro#L14)) and a fixed floating download bar ([FloatingDownloadBar.astro:10](../website/src/components/FloatingDownloadBar.astro#L10)) can cover content; the bar correctly uses `inert`/`aria-hidden` when hidden ([FloatingDownloadBar.astro:60](../website/src/components/FloatingDownloadBar.astro#L60)). No source-level proof establishes focus visibility at 320 CSS px or 400% zoom. **Mapping:** WCAG 1.4.10 and 2.4.11. **Minimal fix:** test focused links and anchor destinations at narrow viewports, and add appropriate scroll offsets or responsive layout if obscured. **Verification:** untested runtime geometry.

### P3 — Minor

15. **Reduced-motion rule slows rather than stops the indefinite browser spinner.** **Confirmed CSS.** The spinner loops indefinitely ([styles.css:133](../src/renderer/src/styles.css#L133)); the reduced-motion rule changes animation duration to 2 seconds without disabling iteration ([styles.css:143](../src/renderer/src/styles.css#L143)). A user who requests reduced motion still sees rotation. The landing page explicitly reduces its animations ([global.css:52](../website/src/styles/global.css#L52)). **Mapping:** user-preference support / EN 301 549 11.7; WCAG 2.3.3 is AAA, not an AA failure by itself. **Minimal fix:** replace rotation with a static loading indicator under reduced motion. **Verification:** CSS only.

16. **Landing-page mock controls look interactive but are inert.** **Confirmed markup; accessibility impact is contextual.** “Mark as read”, “Edit note” and “Remove” are styled as clickable spans without handlers ([FeatureLater.astro:89](../website/src/components/FeatureLater.astro#L89)). They can mislead mouse users and be read as real actions. **Mapping:** WCAG 3.2.4/4.1.2 only if presented as operable controls; avoid assuming a failure for a clearly illustrative mockup. **Minimal fix:** remove pointer/hover styling and identify the illustration, or implement real semantic controls if intended to operate. **Verification:** source.

## Coverage and platform-specific risks

- **Keyboard and focus:** Tab selection, close/pin, tab ordering and Split Right/Below have native context-menu actions; Workspace menus support right-click and Context Menu/Shift+F10; sidebar resizing supports keyboard; Later actions are buttons. See [main.tsx:304](../src/renderer/src/main.tsx#L304), [main/index.ts:763](../src/main/index.ts#L763), [WorkspaceActions.tsx:40](../src/renderer/src/WorkspaceActions.tsx#L40). Verify actual menu invocation from a keyboard, focus after deletion, and keyboard alternatives to every drag target. Split pane ratio adjustment is absent (finding 6).
- **Live views and profile isolation:** `attachVisible` attaches only current-profile Workspace views and settings hides them ([main/index.ts:203](../src/main/index.ts#L203)); Workspace cache retains views and split trees ([main/index.ts:108](../src/main/index.ts#L108), [main/index.ts:390](../src/main/index.ts#L390)). This is not proof inactive pages disappear from UIA/AX trees or that focus/caret survives detach, cache eviction, optimistic switching, rollback, Peek overlays, or profile changes. Confirm cross-profile content is never exposed in the inactive accessibility tree. Electron documents automatic AT detection; lack of a manual toggle does **not** establish that the tree is disabled ([Electron accessibility](https://www.electronjs.org/docs/latest/tutorial/accessibility)).
- **Website semantics:** document language, title, skip link, main landmark, navigation and headings exist ([Layout.astro:24](../website/src/layouts/Layout.astro#L24), [Layout.astro:56](../website/src/layouts/Layout.astro#L56), [index.astro:22](../website/src/pages/index.astro#L22)); decorative ghost SVG is hidden from AT ([GhostIcon.astro:18](../website/src/components/GhostIcon.astro#L18)). No conventional HTML forms or content `<img>` elements were found in `website/src`; assess any CSS/SVG mockups for equivalent meaning. Heading sequence, mobile layout, focus indicators, broken links, and 200%/400% reflow require rendered review. Current configuration marks installers unavailable ([downloads.ts:21](../website/src/config/downloads.ts#L21)); future verified-installer CTA selection defaults to the macOS URL ([Navbar.astro:9](../website/src/components/Navbar.astro#L9)), so platform choice and clear download names need review before release.
- **Other untested browser surfaces:** find result announcements, optimistic switch rollback, keyboard shortcuts/IME and reserved AT keys, download errors, later-note editing, group collapse, popup navigation, page permissions, native dialogs, resizing, colour-only states, focus contrast, OS magnification and text scaling. Custom group colours cannot be presumed to meet non-text contrast. Tooltips based on `title` are not a dependable touch or screen-reader help mechanism.

## Phased remediation

1. **Core usability:** name/announce download progress; make Workspace/Profile and split focus transitions predictable; implement and document keyboard pane navigation; improve browser chrome scaling; fix measured site contrast.
2. **Interaction parity:** resolve tab/touch context-menu access; provide real split resizing or correct site copy; restore focus on panel closure/deletion; audit transient optimistic states and cache eviction; verify menus and emoji picker.
3. **Visual and platform hardening:** verify high-contrast system colours, custom group colours, focus visibility, target size, OS text scaling, browser/page zoom, reduced motion and website reflow; fix observed defects.
4. **Regression and release:** add automated scans and focused Electron/website keyboard journeys; complete the matrix below and retain evidence, versions and manual results. Reassess against each applicable criterion before any conformance claim.

## Phase 2 implementation note (31 October 2026)

Idle now offers 100%, 125% and 150% interface sizes under Settings → Appearance, independently of webpage zoom. The browser renderer scales its chrome; page views receive scaled pane geometry, while webpage zoom remains a separate command. Native menus retain the operating system’s sizing. The sidebar divider hit region increased from 8 to 16 CSS pixels, and the reduced-motion spinner is static. The landing page secondary-text token and low-opacity Split View illustration text were darkened/lightened respectively. The original audit remains a historical snapshot, not a conformance claim.

**Manual verification required:** test each size at the minimum window size and on multi-monitor DPI changes; check split panes, Peek, native menus, popovers, sidebar resizing, titlebar/caption controls and keyboard focus. Verify Windows text scaling and Contrast themes, macOS Larger Text and VoiceOver, and user-defined group colours; Electron/OS scaling is not known to honor every OS text-size preference automatically. The 16 CSS pixel divider remains below the WCAG 2.2 24 CSS pixel nominal target; measure spacing and applicable exceptions. Render and measure all landing-page text and interactive/focus indicators in both themes, reflow and zoom; token calculations alone do not prove contrast conformance.
